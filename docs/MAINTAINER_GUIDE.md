# 维护者指南

## 1. 维护范围

维护分为四类：

1. 网页代码；
2. 二维码协议；
3. 公开编码表；
4. 文档和发布。

四类修改应分别评估。界面修改不应顺带改变协议；数据修订不应顺带重排数组。

## 2. 日常维护流程

### 2.1 接收问题

先确认：

- 工具版本；
- 编码表版本；
- 浏览器；
- 在线或本地运行；
- 是否使用缓存编码表；
- 是否存在自定义字段；
- 是否使用中心图片；
- 是否能提供HEX调试编码；
- 是否能稳定复现。

### 2.2 分类

| 类型 | 处理重点 |
|---|---|
| 页面不加载 | JavaScript语法、加载器、网络和DOM |
| 无编码输出 | 校验、事件绑定、运行时异常 |
| 二维码不可扫 | 原始字节写入、中心图片、纠错和扫码器 |
| 解码字段错误 | 固定边界、数据库索引和缓存版本 |
| 中文乱码 | CJK16边界和二次UTF-8编码 |
| 数据不完整 | 编码表新增、关系或别名 |
| Pages仍是旧版 | 发布源、部署快照和Pages设置 |
| 图片不恢复 | localStorage容量、Data URL和显式移除逻辑 |

### 2.3 修复

- 先复现，再修改；
- 保留最小测试样例；
- 不把多个独立问题混为一个补丁；
- 避免运行时覆盖旧函数造成双路径；
- 修改事件和DOM时做真实浏览器测试；
- 生成文件后再次从最终包中运行，而不是只测试源文件。

## 3. 编码表发布

发布前执行：

- JSON语法校验；
- 六张索引表旧代码和顺序对比；
- 新代码唯一性检查；
- 引用完整性检查；
- 关系类型检查；
- `version`和`updatedAt`检查；
- 网页同步测试；
- 旧二维码映射抽样测试。

禁止通过排序工具自动重排整个JSON。

## 4. 工具发布

### 必测记录

至少准备：

1. 全数据库字段；
2. 空烘焙商；
3. 三个中文烘焙商；
4. 中英文混合烘焙商；
5. 纯自定义必填字段；
6. 数据库与自定义混合；
7. 无自定义记录；
8. 日期最大值；
9. 超日期范围；
10. 图片上传和裁切；
11. 刷新后本地恢复；
12. 明确移除图片；
13. CRC篡改。

### 必查输出

- 页面版本；
- 自检结果；
- 总字节数；
- 固定主体32字节；
- CRC；
- 自定义标记；
- 解码还原；
- 二维码Canvas；
- 控制台错误。

## 5. 版本管理

版本号不是提交次数。

通常需要提升功能版本的情况：

- 新增用户可见能力；
- 改变协议；
- 改变数据结构；
- 改变兼容行为；
- 重要浏览器兼容性变化。

通常不必提升工具版本：

- README恢复；
- 拼写修订；
- 不改变行为的测试补充；
- 维护公告更新。

编码表新增索引行时提升编码表`version`，但不一定提升工具版本。

## 6. 发布和回退

发布前保存：

- 正式HTML；
- ZIP部署包；
- SHA-256；
- 测试报告；
- 上一版文件；
- 提交SHA。

发现严重问题时：

1. 停止继续叠加修补；
2. 回退到最近已验证版本；
3. 保存失败样例；
4. 确认问题属于代码、数据还是部署；
5. 修复后重新完成全链路测试。

## 7. GitHub Pages

Pages发布源固定为：

```text
main / (root)
```

仓库文件更新而网页未更新时：

1. 检查仓库目标文件内容；
2. 检查Pages源；
3. 将Branch设为None并保存；
4. 再恢复`main / (root)`；
5. 检查公开页面源代码；
6. 不要先把问题归因于浏览器缓存。

## 8. 审核原则

维护者可以拒绝：

- 无来源数据；
- 破坏行号的整理；
- 无真实浏览器测试的功能修改；
- 过度复杂但无容量收益的协议；
- 无迁移方案的兼容性破坏；
- 把自定义数据自动上传的设计；
- 无法解释边界的二进制编码。

维护判断应记录理由，保持规则一致。
