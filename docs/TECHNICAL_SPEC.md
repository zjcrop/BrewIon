# BrewIon v3.0技术规范

## 1. 设计目标

二维码协议必须同时满足：

- 信息可逆；
- 字节长度可控；
- 中文烘焙商高效；
- 数据库索引稳定；
- 支持未收录信息；
- CRC可检测误码和篡改；
- 不依赖字段连接符；
- 旧记录不因数据库重排而失效。

## 2. 逻辑包结构

### 2.1 无自定义内容

```text
[固定主体32字节][烘焙商CJK16 0..N字节][CRC16 2字节]
```

### 2.2 有自定义内容

```text
[固定主体32字节]
[烘焙商CJK16 0..N字节]
[0xFF]
[自定义信息UTF-8 1..240字节]
[CRC16 2字节]
```

`0xFF`是自定义扩展区标记。CJK16编码规则不把`0xFF`作为正常字符起始字节，因此可以确定边界。

|---:|---|---:|
| 1 | 国家索引 | 2 |

| 7 | 烘焙信息 | 2 |
| 8 | 海拔 | 2 |
| 9 | 风味1 | 2 |
| 10 | 风味2 | 2 |

空字段使用固定宽度占位，不通过删除字段缩短主体，因此解析不需要连接符。

## 4. 行号编码

数据库字段按数组稳定行序编码。一般规则：

- 行号从1开始；
- 使用Base36字符；
- 不足宽度使用`*`左补齐；
- 全空字段使用相同宽度的`*`；
- 不允许既有行重排。

示例：

```text
1   → *1
35  → *Z
36  → 10
460 → *CS
空2字节 → **
空3字节 → ***
```

## 5. CJK16

### 5.1 ASCII

`U+0000`至`U+007F`直接使用1字节。

### 5.2 CJK基本区

`U+4E00`至`U+9FFF`映射到16位值：

```text
v = 0x8000 + (codePoint - 0x4E00)
```

按大端序写入2字节。

### 5.3 CJK扩展A

`U+3400`至`U+4DBF`映射到：

```text
v = 0xD200 + (codePoint - 0x3400)
```

按大端序写入2字节。

### 5.4 其他Unicode

使用转义：

```text
FE + UTF-8长度 + UTF-8字节
```

保留范围不得被普通字符占用。

## 6. 自定义文字

自定义字段按可读形式序列化：

```text
字段名=规范化文字
```

多字段以换行分隔。

规范化包括：

- Unicode NFC；
- 回车、换行和制表符转为空格；
- 连续空格压缩；
- 去除首尾空白；
- 限制UTF-8总字节数。

自定义内容不参与官方数据库索引。

## 7. 日期

烘焙日期使用三位Base36压缩。支持范围：

```text
2000-01-01 ～ 2127-09-27
```

最大值：

```text
ZZZ
```

超出范围必须拒绝编码。

## 8. CRC

算法：

```text
CRC16-CCITT
初始值：0xFFFF
多项式：0x1021
输出：大端序2字节
```

标准测试向量：

```text
"123456789" → 0x29B1
```

CRC覆盖：

```text
固定主体 + 烘焙商CJK16 + 可选FF标记 + 可选UTF-8扩展
```

## 9. QR段模式

固定主体由ASCII组成，可使用QR Alphanumeric模式提高容量效率。

烘焙商、扩展区和CRC必须作为原始Byte模式写入。不得把大于127的字节先转换成JavaScript字符串再交给普通`addData()`，否则可能发生UTF-8二次编码。

扫码时应优先读取原始字节，例如支持`binaryData`的解码结果。仅返回文本的扫码器可能无法完整保留二进制数据。

## 10. 中心图片

中心图片不是协议内容：

- 不进入逻辑包；
- 不参与CRC；
- 不改变同一信息的编码字节；
- 只影响二维码图像矩阵的可读冗余。

中心图片越大，扫码失败风险越高。应结合纠错等级、打印尺寸和扫描环境验证。

## 11. 兼容性规则

任何协议修改必须回答：

1. 旧二维码能否解码；
2. 新二维码能否被旧工具识别；
3. 字段边界是否变化；
4. 数据库行号是否变化；
5. 是否需要迁移；
6. 是否需要版本标记；
7. 如何回退。

没有完整迁移和测试方案，不得改变固定主体顺序和宽度。
